## 4. Champ session_id dans upstream_body (app.py)

L’unique création du SID est `session_id = sio.get_sid('/')` à `app.py:684`. Il est ensuite utilisé une seule fois, dans `upstream_body`, à `app.py:691` sous la forme `'session_id': session_id`. La socket est connectée en transport WebSocket à `app.py:673–675`. Ce SID est donc d’origine Socket.IO, pas un identifiant métier de discussion dans le code Coach.

**Recommandation : Option 1 — retirer complètement `session_id` du corps HTTP**, sous réserve de vérifier que le handler de la version Open WebUI déployée accepte l’absence de ce champ. Si la logique décrite dans la demande est confirmée — lecture par `request_info.get('session_id')`, recherche `SESSION_POOL.get(...)`, puis transmission de cette valeur à `skip_sid` — l’omission évite de donner à Open WebUI le SID de la socket qui doit précisément recevoir l’événement. Une constante comme `'coach-bridge'` (Option 2) est moins sûre : elle suppose sans preuve qu’elle ne peut jamais correspondre à un SID actif et que le code traite un SID inconnu comme absence de SID.

Limite importante : `/app/backend/open_webui/socket/main.py` n’est pas lisible dans l’environnement de cette mission. L’affirmation sur `SESSION_POOL`, `skip_sid`, la ligne ~1502 et le comportement lorsque `session_id` est omis est donc **à confirmer** sur le code du conteneur/version réellement déployée. Les lignes 1490–1560 ne peuvent pas être citées indépendamment ici. À partir du seul extrait décrit dans la demande, Option 1 est la recommandation conditionnelle; avant déploiement, vérifier le contexte exact et le chemin d’absence de champ. Ne pas remplacer le SID Socket.IO par `id_discussion` : l’identifiant métier doit voyager dans le bridge/context, pas occuper le champ de contrôle Socket.IO.
