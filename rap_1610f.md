# Diagnostic /api/chat — 2026-10-16

## 1. Symptôme observé

Le symptôme rapporté est un POST `/api/chat` qui reçoit HTTP 200, sans réponse visible ni ligne applicative correspondante. Un 200 signifie ici que FastAPI a retourné la `StreamingResponse` (app.py:899–902), pas que le relais a reçu ou livré une réponse. Le navigateur ne rend le texte final qu’après `settled` et `done` (static/app.js:95–103, 115–119). L’absence de log ne prouve pas à elle seule que la route n’a pas été exécutée : plusieurs chemins d’attente et de filtrage ne journalisent rien (app.py:740–760, 885–889).

Périmètre : lecture du code et des rapports déjà présents dans le dépôt seulement. Aucun appel à Open WebUI ni inspection de la configuration effective du service n’a été fait. La réaction de l’instance installée à un tool ID inconnu n’est donc pas établie.

## 2. Hypothèses classées par probabilité

### 1. Les événements Socket.IO sont reçus mais rejetés par le filtre d’identifiants

Après connexion, Coach crée `chat_id = temporary:<UUID>` et `assistant_id = <UUID>` (app.py:681–684). Le corps HTTP envoie exactement le premier dans `chat_id` et le second dans `id` (app.py:685–691). L’API Socket.IO reçoit ses événements dans `on_openwebui` (app.py:669–671), mais la boucle exige que les champs de l’événement soient `chat_id` et `message_id` et égalent ces valeurs (app.py:757–760). Les événements sans ces champs, enveloppés différemment, ou portant un identifiant différent sont ignorés sans log et sans SSE. Aucun événement accepté signifie attente jusqu’à 185 secondes, puis SSE `error` « Le flux du modèle a expiré » sans log dédié (app.py:733–746). Le client supprime alors le message assistant vide et affiche l’erreur (static/app.js:101, 121–124). Si l’observation intervient avant le délai, le message peut rester vide.

Cohérence : les valeurs du corps HTTP sont cohérentes entre elles et le contrat attendu par le code de Coach (`id` est l’ID assistant transmis, `message_id` est la clé attendue à la réception). Cela ne démontre pas que l’instance Open WebUI renvoie ces mêmes valeurs au niveau supérieur de l’événement `events`; cette forme effective reste à vérifier.

Signature logs : aucune ligne spécifique pour le filtre ou le timeout. Signature client : aucun événement SSE au fil de l’attente, puis `error` au délai ; jamais `settled`/`done`.

### 2. Open WebUI rejette la requête HTTP, possiblement à cause de `tool_ids`

`OPENWEBUI_TOOL_IDS` est découpée sur les virgules, les éléments vides supprimés et la liste ajoutée à `upstream_body['tool_ids']` si non vide (app.py:708–710). Coach ne vérifie ni existence, ni association, ni autorisation de ces IDs. `relay()` lance le POST HTTP en tâche (app.py:735–738), puis émet `ready` (app.py:739). Si aucun événement Socket.IO ne survient pendant un intervalle de 250 ms et que la tâche HTTP est terminée, Coach vérifie son statut (app.py:742–754). Une exception HTTP (dont `raise_for_status`) ou un objet JSON `{"status": false}` produit le log `upstream_error`, SSE `error` « Réponse du modèle indisponible », puis fin (app.py:719–728, 747–753). Le navigateur affiche le message d’erreur générique et enlève la bulle vide (static/app.js:101, 121–124).

À l’inverse, le code ne permet pas de conclure qu’un ID inconnu sera rejeté en HTTP : Open WebUI peut aussi accepter la requête, retourner un événement `chat:message:error`, ne produire aucune complétion, ou ignorer les tools. Ces comportements dépendent de la version et de la configuration Open WebUI et ne sont pas observés dans les artefacts de code Coach. Si un événement `chat:message:error` correspondant passe le filtre, Coach le relaie en SSE `openwebui`, puis émet SSE `error` « La réponse du modèle a été interrompue » (app.py:817–820); il n’écrit pas de log dans cette branche. Si Open WebUI accepte la requête HTTP mais ne produit ni complétion ni erreur Socket.IO recevable, la tâche HTTP est acquittée puis la boucle attend sans log jusqu’au timeout SSE (app.py:747–755, 733–746). Si l’erreur Socket.IO ne satisfait pas le filtre, elle est simplement ignorée (app.py:757–760).

Signature logs : `status=upstream_error` seulement pour rejet/exception HTTP observé durant une attente sans événement, avec statut et résumé de corps redacté si disponibles (app.py:89–97, 750–752). Aucun log n’est garanti pour une erreur Socket.IO. Signature client : `ready`, éventuellement `openwebui` puis `error`; ou `ready` puis `error` au timeout.

### 3. Connexion ou autorisation Socket.IO invalide

La connexion utilise `OPENWEBUI_SOCKET_TOKEN` ou, en repli, `OPENWEBUI_API_KEY` sauf si celle-ci commence par `sk-`; un jeton absent ou de type `sk-` déclenche HTTP 503 avant la réponse de streaming (app.py:659–664). L’échec réel de `sio.connect` écrit `status=socket_error`, puis HTTP 502 (app.py:666–679). Donc ces deux causes ne cadrent pas avec un POST aboutissant à HTTP 200, à moins que le statut rapporté provienne d’une requête différente ou d’un intermédiaire. Un token accepté pour Socket.IO mais associé à un autre contexte/format pourrait aussi laisser les événements attendus absents; le code ne peut pas en déterminer la cause, et l’attente serait silencieuse (app.py:673–675, 740–760).

Signature logs : `socket_error` en cas d’échec de connexion; aucun log nécessaire si connexion établie mais événements manquants. Signature client : réponse HTTP non-200 pour l’échec de connexion; sinon `ready`, puis attente et potentiellement `error` de timeout.

### 4. Erreur ou réponse incomplète après réception d’une complétion

Pour une complétion, le code agrège deltas/contenu et marque la réponse complète selon `done`, ou les événements Responses `response.completed`/`response.done` (app.py:765–816). Une complétion vide ou avec `finish_reason == 'length'` produit `openwebui`, puis SSE `error` « Réponse du modèle incomplète », sans log (app.py:822–827). Si la validation HTTP finale, l’extraction ou le règlement lève une exception, le chemin général écrit `stream_error` et émet SSE `error` (app.py:828–832, 885–892). Une erreur SQLAlchemy au débit a son propre log `charge_error`, puis SSE `error` « Débit impossible » (app.py:865–876). Ces chemins supposent un événement arrivé et cadrent donc moins avec l’absence totale de lignes et de réponse.

Signature logs : aucune pour réponse vide/coupée; `stream_error` pour exception générale; `charge_error` pour échec SQLAlchemy au règlement. Signature client : `openwebui`, puis `error`; pas de `settled` ni `done`.

### Test raisonné demandé : ID Open WebUI inconnu

Sans exécuter : Coach le transmet sans validation sous `tool_ids` si la liste est non vide (app.py:708–710). Puis le flux suit l’un des chemins ci-dessus, selon la réponse effective d’Open WebUI : rejet HTTP/JSON false → `upstream_error` + SSE `error` (app.py:747–753); `chat:message:error` bien corrélé → SSE `openwebui`, SSE `error` (app.py:817–820); aucune complétion/erreur recevable → flux arrêté côté client seulement au timeout de 185 secondes, SSE `error`, sans log applicatif dédié (app.py:733–746); événement mal corrélé → événements ignorés jusqu’au même timeout (app.py:757–760). Le code source seul ne permet pas de choisir parmi ces issues. Le flux serveur s’arrête alors à la branche `return` correspondante de `relay()`; en cas de silence, il s’arrête au timeout. Une exception pendant les opérations de relais est absorbée par le `except` général qui envoie `error` (app.py:890–892).

## 3. Ce qu'il faut vérifier en premier

1. Dans DevTools → Network → requête `/api/chat` → Response, observer le flux pendant au moins 190 secondes. Résultat attendu : `ready` confirme le démarrage de `relay()` (app.py:739). Si la réponse contient immédiatement `error`, noter son `detail`; si elle reste sans événement jusqu’au timeout, cela confirme une attente sans événement accepté. La page masque la bulle vide et affiche alors le texte d’erreur (static/app.js:121–124).
2. Dans DevTools, capturer les événements Socket.IO `events` émis par l’instance pendant cette même requête et comparer les champs de premier niveau `chat_id`/`message_id` avec le `chat_id` et le `id` envoyés au POST `/api/chat/completions`. Résultat attendu si l’hypothèse 1 est vraie : événement présent, mais champ absent ou valeur différente des IDs de cette requête (app.py:681–691, 757–760). Ne pas partager les tokens/cookies ou contenus utilisateur lors de cette inspection.
3. Vérifier dans le panneau Network la requête backend `/api/chat/completions` : statut HTTP et corps de réponse (sans exposer de secret). Statut non-2xx ou JSON `status: false` devrait correspondre à `upstream_error` si aucun événement n’a précédé (app.py:719–728, 747–753). HTTP 2xx n’établit pas qu’une complétion Socket.IO a été émise.
4. Vérifier dans l’interface d’administration Open WebUI que chaque ID configuré existe et est disponible pour le modèle sélectionné; comparer avec les IDs réellement envoyés, sans copier de secrets. Un ID invalide plus un `chat:message:error` corrélé devrait se traduire par SSE `openwebui` puis `error` (app.py:817–820); un rejet HTTP par la signature de l’étape 3; une absence d’événement recevable par l’attente silencieuse de l’étape 1.
5. Lire `journalctl -u coach.service` autour de l’heure exacte de la requête, sans imprimer les variables d’environnement. `upstream_error`, `stream_error` ou `socket_error` permet de distinguer les branches de code; aucune de ces lignes n’est attendue pour filtre strict, erreur Socket.IO, réponse incomplète, ou timeout (app.py:677–679, 747–753, 817–827, 885–892). Ne pas relancer le service.
6. Vérifier la requête exacte (méthode, `Content-Type`, présence cookie de session, statut HTTP réel, modèle, structure JSON) et la console navigateur. Cela écarte une mauvaise corrélation entre le POST observé et les logs recherchés. Les erreurs pré-stream apparaissent en HTTP non-200, pas en événements SSE (app.py:623–664); une session absente produit normalement 401 via `current_user` (app.py:380–385).

## 4. Correctif probable

L’hypothèse la plus probable au vu du symptôme strict « 200, aucun log, rien n’apparaît » est une requête HTTP acceptée suivie d’événements Socket.IO absents ou rejetés par le filtre, notamment si l’erreur liée au tool ne porte pas les deux IDs attendus. Ce classement est une inférence à partir du silence décrit et du code, pas une preuve que l’ID est invalide.

Correctif minimal proposé après confirmation des événements : dans `app.py:757–760`, traiter les événements d’erreur/cancellation corrélés par `chat_id` même si `message_id` manque ou diffère, et journaliser de manière non sensible le motif/compteur des événements écartés (sans contenu, token ou ID utilisateur). Si la capture montre au contraire qu’Open WebUI rejette `tool_ids`, retirer l’ID erroné de `OPENWEBUI_TOOL_IDS` dans la configuration, puis appliquer le processus de redémarrage par le propriétaire. Aucun changement n’est appliqué ici. Il faut confirmer le chemin réel avant de choisir entre ces ajustements.

## 5. Points de fragilité identifiés

- La tâche HTTP a un timeout de 180 s (connexion 15 s) tandis que l’échéance SSE est 185 s (app.py:733–738). La vérification de `submit_task.done()` ne se produit que lors d’une attente de 250 ms sans événement (app.py:742–755); un flux d’événements continus mais non terminaux peut retarder l’examen d’une réponse HTTP déjà terminée.
- Les événements non-dictionnaires et tous les événements ne correspondant pas aux deux IDs sont ignorés sans log ni compteur (app.py:757–760). C’est le chemin de silence le plus net.
- Le chemin `chat:message:error`/`chat:tasks:cancel` relaie l’erreur puis termine, mais n’écrit pas de log serveur (app.py:817–820). Les clients qui ne comprennent pas les événements `openwebui` restent dépendants du SSE `error` émis ensuite.
- `ready` signifie seulement que la réponse SSE a commencé, pas que le POST amont a été accepté (app.py:735–739).
- Une réponse SSE d’erreur garde le statut HTTP initial 200; le JavaScript ne regarde plus `response.ok` après le début du flux et traite `error` via SSE (static/app.js:76–83, 101). Cela correspond au symptôme réseau rapporté.
- Les branches de timeout et de réponse incomplète émettent une erreur SSE sans log applicatif spécifique (app.py:742–746, 822–827). La tâche amont est annulée dans `finally` si elle est encore en cours (app.py:893–897).
- La requête ne suit pas l’événement `chat:message:error` si son `message_id` est différent, car le filtre précède le décodage du type (app.py:757–763). Un événement d’erreur pertinent peut donc être silencieusement perdu.
- L’appel amont est lancé en tâche indépendante. Si un événement terminal arrive avant la fin de la tâche HTTP, le `await submit_task` peut lever et rejoindre le chemin `stream_error`; la facturation ne commence qu’après cet await et la validation du contenu (app.py:822–832).
- Le code retire les données sensibles connues des logs d’erreur HTTP et exception (app.py:63–97), mais n’écrit jamais le corps HTTP complet, ce qui limite le diagnostic des réponses d’erreur. Les messages fournis par Open WebUI peuvent être exposés au navigateur via l’événement `openwebui` et son rendu (app.py:817–822; static/app.js:94, 365); ne pas supposer que les détails d’outil sont toujours neutres.
- `chat()` lit les variables suivantes (app.py:632, 635, 655–660, 708–710) : `OPENWEBUI_COACH_MODELS` (absence/liste vide ou modèle absent → 403), `OPENWEBUI_FREE_MODELS` (absence → modèle payant; valeur incorrecte peut classer à tort un modèle comme gratuit), `OPENWEBUI_BASE_URL` et `OPENWEBUI_API_KEY` (absence/vide → 502 avant streaming), `OPENWEBUI_SOCKET_TOKEN` (absence : repli sur API key seulement si elle n’a pas le préfixe `sk-`; absence finale ou préfixe `sk-` → 503; token invalide à la connexion → log `socket_error` et HTTP 502), `OPENWEBUI_TOOL_IDS` (absence/vide → aucune clé `tool_ids`; chaînes non vides sont transmises telles quelles après découpe/trim; ID invalide a les résultats Open WebUI non établis plus haut). Ce sont les variables d’environnement directement lues par `chat()`; les tarifs et le solde viennent aussi de la base, pas de l’environnement (app.py:637–654).
- JSON illisible → HTTP 400; modèle de mauvais type → HTTP 422; messages invalides → HTTP 400; modèle hors allowlist ou tarif manquant pour un modèle non gratuit → HTTP 403; tarif incohérent → 503; solde insuffisant → 402 (app.py:623–654). Ces cas ne produisent pas d’événements SSE. Une fois la réponse 200 démarrée, les erreurs de flux deviennent des événements SSE (app.py:899–902).
- La session SQLAlchemy ouverte par les lectures est explicitement rollbackée avant le flux; le débit payant s’effectue ensuite via `charge_response`, écriture de solde et journal atomique (app.py:712–713, 275–311). Le chemin de modèle gratuit n’écrit aucun débit et retourne le solde lu avant le flux (app.py:650, 840–846). Ces éléments ne semblent pas expliquer une absence d’événement en amont.
