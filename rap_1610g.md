## 2. Nouvelle architecture cible

Le POST navigateur reste `/api/chat` et garde la même signature FastAPI (app.py:619–620). Son corps évolue de `{model, messages}` (static/app.js:76) vers `{model, discussion_id, messages}`. Coach authentifie l’utilisateur de la même façon via `Depends(current_user)` (app.py:620); aucun changement de cookie/session utilisateur n’est attendu.

Coach valide le JSON, le modèle, les messages et le `discussion_id`; calcule le pré-contrôle; puis injecte au début du contexte transmis un message système construit côté serveur. Open WebUI reçoit directement un POST HTTP streamé `/api/chat/completions` avec au minimum `model`, `messages` et `stream: true`. Il ne reçoit plus `chat_id`, `id`, `session_id`, `user_message` ou `user_message_id`. Le test décrit dans la demande établit que le corps minimal sans ces IDs produit un SSE HTTP OpenAI-compatible. La compatibilité simultanée de `tool_ids` avec le stream HTTP direct est à confirmer; le test fourni établit son chargement en mode `stream:false`, pas explicitement avec `stream:true`.

`relay()` lit les octets du corps à mesure, reconstruit les lignes/blocs SSE OpenAI, parse chaque objet `data:` JSON, agrège `choices[0].delta.content`, retient le dernier objet `usage` et `cost`, puis traite `[DONE]` comme fin de réponse. Les chunks utiles sont retransmis au navigateur sous l’event Coach `openwebui`, dans une enveloppe compatible avec `renderOpenWebUIEvent`.

À la fin : vérifier qu’un contenu non vide et une fin complète ont été reçus; établir les tokens depuis `usage`; si `usage.cost` est présent, garder `provider_debit_micro_usd`; sinon appliquer le fallback estimé/maximal selon les tokens et la politique actuelle (app.py:836–867); appeler `charge_response` seulement après complétion valide (app.py:868–879); émettre `settled`, puis `done`. Une coupure ou erreur ne doit pas lancer une charge sans réponse complète. En modèle gratuit, conserver `settled` avec charge zéro.

Exemple structurel court, non exécutable complet :

```text
messages = [{role: system, content: instruction + discussion_id}, ...messages_validés]
POST /api/chat/completions {model, messages, stream: true}
pour chaque bloc SSE: parser data; si JSON -> agrégat + event Coach openwebui
si [DONE]: valider réponse -> charge_response -> settled -> done
```

Le message système devrait transmettre uniquement la valeur opaque et l’instruction d’appeler le tool avec cette valeur. Le format exact de l’instruction et le nom du champ que le tool externe attend sont **à confirmer** avec le tool Open WebUI. Coach doit aussi limiter `discussion_id` (par exemple UUID canonique) et s’assurer que le contexte existe/est autorisé; les routes de contexte imposent l’utilisateur connecté et renvoient 404 si le contexte n’existe pas (services/context_payload.py:49–55; app.py:1118–1124).

## 3. Plan de refonte de chat()

1. **Lire et valider la requête** — conserver le parsing JSON et erreurs actuelles (app.py:623–631). Exiger `model`, `messages`, et ajouter `discussion_id`. Rejeter une valeur absente, vide, trop longue ou au format inattendu en HTTP 400/422 avant de commencer le SSE. Si l’ID est un UUID choisi par le front, le valider comme UUID; le format exact reste à arrêter avec la création des discussions et le tool.
2. **Valider l’historique puis injecter le système** — garder les règles de `validate_chat_messages` (app.py:246–265), et ne pas permettre au navigateur de fournir le rôle `system`. Coach construit lui-même une instruction contenant le `discussion_id`, puis envoie `[system, ...messages]`. Compter les caractères du système injecté dans la pré-autorisation maximale actuellement calculée sur `input_characters` (app.py:631, 643–646), ou choisir une marge fixe documentée; autrement le `max_charge` sous-estime l’entrée réellement facturable si `usage` manque.
3. **Conserver les contrôles produit** — allowlist modèle, gratuité, tarif actif, solde, `OPENWEBUI_BASE_URL` et API key gardent leurs contrôles actuels (app.py:632–658). Supprimer le besoin du JWT Socket.IO et ses erreurs 503/502 (app.py:659–684). L’authentification navigateur `current_user` reste identique.
4. **Construire le POST amont** — corps minimal `{model, messages: [...], stream: true}`. Retirer le bloc UUID et `user_message`; garder `tool_ids`, `params.function_calling` et `max_tokens` seulement s’ils ont été vérifiés nécessaires/compatibles pour SSE HTTP. Aucun des champs `chat_id`, `id`, `session_id`, `user_message`, `user_message_id` ne doit être transmis selon la décision actée. Garder `request_id` pour `credit_ledger` et `db.rollback()` avant stream (app.py:711–716).
5. **Ouvrir le stream HTTP** — dans le générateur `relay`, ouvrir le POST avec `httpx.AsyncClient.stream('POST', ..., json=upstream_body, timeout=...)`. Contrôler `raise_for_status()` avant de considérer le stream valide. Émettre `ready` au moment où la réponse amont a été établie, et pas seulement après la création d’une tâche locale (actuellement ready est émis avant acceptation, app.py:738–742).
6. **Parser les blocs SSE** — bufferiser les octets jusqu’à séparateur de lignes vides (`\n\n` ou `\r\n\r\n`), préserver le reliquat entre lectures, décoder UTF-8 en mode incrémental, joindre les lignes `data:` selon SSE. Ignorer commentaires/lignes sans data. Reconnaître `[DONE]`; parser les autres data comme JSON et traduire les erreurs JSON en erreur de flux contrôlée. Ne pas perdre un dernier bloc non terminé proprement à EOF.
7. **Agréger et retransmettre** — pour les chunks OpenAI, concaténer seulement les `choices[].delta.content` de type string; capturer `finish_reason`, et mettre à jour l’usage dès qu’un chunk fournit `usage`. Émettre pour le front `openwebui` avec `{type:'chat:completion', data:<chunk>}` afin que `static/app.js:303–340` continue de traiter les deltas et le format OpenAI.
8. **Finaliser la réponse** — ne considérer `[DONE]` comme suffisante que si la réponse possède du texte et n’est pas incomplète (`finish_reason == 'length'`). Le comportement de finish_reason peut être absent sur certains flux; conserver l’évaluation prudente et documenter les cas tolérés.
9. **Régler** — reprendre les règles actuelles d’extraction de `prompt_tokens`/`completion_tokens` et `cost` (app.py:836–867). Si le coût fournisseur est valide, calculer avec le coût réel; si absent, tokens présents → estimation tarifaire; si usage/tokens absents → `max_charge`, loguer explicitement l’estimation maximale. S’assurer que le `max_charge` comprend l’instruction système injectée. Écrire via `charge_response` (app.py:275–311) puis envoyer `settled` avec le contenu final, débit et nouveau solde; ensuite `done`.
10. **Erreurs et annulation** — HTTP amont 4xx/5xx, exception réseau, réponse SSE invalide, `[DONE]` absent/EOF, timeout et erreur de facturation doivent produire `error` côté SSE après ouverture HTTP 200, avec une erreur non sensible et log cohérent. Sur déconnexion navigateur, annuler/fermer le flux HTTP amont et ne pas facturer une réponse non terminée. Retirer le `finally` Socket.IO et conserver la fermeture garantie du stream.

## 4. Format des events SSE vers le front

Le format ci-dessous conserve les noms consommés par `static/app.js:86–103`; les événements `ready` sont ignorés fonctionnellement par le front, `openwebui` sert au rendu progressif, `settled` et `done` terminent le rendu, `error` lève une erreur UI.

| nom d’event | charge utile | moment d’émission |
|---|---|---|
| `ready` | `{"status":"connected"}` | Une fois le statut HTTP amont vérifié et le stream SSE ouvert. Éviter l’émission avant de savoir si l’upstream a répondu 2xx. |
| `openwebui` | `{"type":"chat:completion","data":<chunk OpenAI JSON>}` | Pour chaque chunk SSE JSON reçu et parsé. Contient notamment `choices[0].delta.content`; le chunk d’usage final peut aussi être relayé. Enveloppe attendue par `renderOpenWebUIEvent` (static/app.js:303–340). |
| `settled` | `{"content":"…","charged_micro_usd":N,"balance_micro_usd":N}` | Après `[DONE]`, validation du contenu et règlement DB; pour modèle gratuit, coût zéro comme actuellement (app.py:843–846). |
| `done` | `{"ok":true}` | Après `settled`, une fois toutes les étapes réussies. Le lecteur JS sort de sa boucle à cet event (static/app.js:101–115). |
| `error` | `{"detail":"Réponse du modèle indisponible"}` ou détail générique approprié | Sur HTTP amont non-2xx, erreur SSE/JSON, timeout, coupure/incomplétude ou règlement impossible. Aucun `settled` ni `done` ensuite. Le front retire la bulle et montre le message (static/app.js:101, 121–124). |

`[DONE]` est un marqueur du protocole SSE OpenAI amont et ne doit pas être transmis comme donnée JSON `openwebui`; il déclenche la finalisation côté Coach. Ne pas émettre de `settled` avant le commit du débit réussi.

## 5. Changements de contrat front ↔ app.py

- **Ajout du champ `discussion_id`** : `static/app.js` envoie aujourd’hui `{model, messages}` (static/app.js:76); le contrat cible devient `{model, discussion_id, messages}`. `app.py:627–631` devra lire et valider ce champ. Le champ doit être stable entre les tours appartenant à la même discussion, pas régénéré à chaque POST.
- **Source suggérée** : le navigateur crée un UUID lors de la création d’une nouvelle discussion et le garde avec `conversation` en mémoire. L’app n’a aujourd’hui qu’un tableau `conversation` volatile (static/app.js:6); aucun mécanisme de création/persistance/reprise de discussion n’est visible dans le front consulté. Le comportement souhaité après rechargement, nouvel onglet ou perte de mémoire est à confirmer. Si l’ID doit retrouver une sélection de contexte existante, le front doit réutiliser son ID de discussion et ne pas en générer un nouveau pour chaque message.
- **Validation serveur** : valider type chaîne, longueur/formalisme (UUID si ce format est retenu), et associer le contexte à l’utilisateur authentifié. Le routeur payload confirme l’existence du contexte pour cet utilisateur (services/context_payload.py:49–55; app.py:1118–1124). Réponse HTTP 400/422 avant streaming si ID invalide; ne pas accepter un `discussion_id` arbitraire pour accéder aux données d’un autre utilisateur.
- **Retraits côté upstream** : le navigateur ne connaissait pas les IDs temporaires; le changement concerne seulement le corps interne envoyé par Coach à Open WebUI. Retirer `chat_id`, `id`, `session_id`, `user_message` et son ID à la construction app.py:686–710. Le `discussion_id` ira dans le message système du modèle, pas dans un champ de protocole Open WebUI non vérifié.
- **Temps réel navigateur** : aucun changement de nom d’event SSE n’est nécessaire. Le parser frontend gère déjà `openwebui`, `settled`, `error`, `done` (static/app.js:86–103). Il peut continuer à recevoir les deltas si Coach conserve l’enveloppe `{type:'chat:completion', data: chunk}`. `ready` est actuellement toléré/ignoré.
- **Authentification** : aucun changement attendu au cookie Coach ni à `current_user` (app.py:380–385, 620). L’appel HTTP amont garde `Authorization: Bearer <OPENWEBUI_API_KEY>` (actuellement app.py:739–741). Retirer l’auth Socket.IO ne doit pas réduire la vérification d’accès au bridge, qui continue à exiger l’utilisateur côté routes de contexte (app.py:1118–1124).
- **Facturation** : aucune modification attendue du principe de débit après réponse complète ni du journal (app.py:275–311, 836–887). L’usage `cost` a été observé par les tests décrits dans le contexte comme présent dans le dernier chunk avant `[DONE]`; le code devra le capturer avant finalisation. Si coût absent/invalide : usage tokens → estimation existante; usage manquant → `max_charge` (app.py:851–867). La pré-autorisation devra toutefois intégrer la longueur du message système nouvellement injecté (app.py:643–646).

## 6. Points de fragilité / à confirmer

- **Format upstream SSE** : la forme OpenAI-compatible décrite (`choices[].delta.content`, chunk final avec usage, `[DONE]`) a été observée dans les essais fournis, mais elle peut varier selon version, provider, tools ou configuration. Le relais doit tolérer chunk sans `choices`, `delta.content` absent, `usage` séparé, CRLF et blocs multi-lignes.
- **SSE fragmenté** : les lectures TCP ne correspondent pas aux chunks SSE. Parser avec un buffer incrémental; conserver les fragments de ligne/bloc et décoder UTF-8 incrémentalement. Traiter une fin EOF sans `[DONE]` comme flux incomplet, sauf protocole upstream confirmé différent.
- **Tool en streaming HTTP** : les éléments fournis prouvent que `tool_ids` charge le tool en `stream:false`, et qu’un body minimal sans IDs produit SSE en `stream:true`; la combinaison `tool_ids` + stream HTTP direct n’est pas explicitement établie dans les faits fournis. À confirmer avant de considérer l’appel du bridge opérationnel. Vérifier également si `params.function_calling='native'` est nécessaire ou supporté sur le chemin minimal.
- **Usage/cost manquant** : `cost` absent ou invalide doit utiliser l’estimation actuelle ou `max_charge`; ne jamais convertir de l’argent en float ni facturer deux fois. Si usage tokens est absent mais le texte complet existe, la politique actuelle facture le maximum et logue `usage_tokens_missing` (app.py:859–867). Le pré-contrôle doit tenir compte du message système et du plafond de sortie.
- **Gestion des erreurs HTTP** : les réponses 4xx/5xx doivent être testées avant parsing du corps; ne pas essayer de parser un JSON d’erreur comme chunk SSE. Le statut navigateur restera 200 si `StreamingResponse` est déjà démarrée; rendre un `error` SSE explicite comme aujourd’hui. Redacter les corps et secrets dans logs.
- **Timeouts** : remplacer le timeout global/délai de 185 s lié à la Queue (app.py:736–749) par timeouts HTTP connect/read/write/pool explicites. Le timeout de lecture doit tolérer les pauses outil, sans laisser un flux bloqué indéfiniment. À confirmer avec durée des appels tool.
- **Facturation et coupure** : ne facturer qu’après un marqueur de fin et validation du contenu. Une coupure après réception d’un texte presque complet mais avant `[DONE]` ne prouve pas une complétion facturable selon le design acté; la règle de charge reste zéro si le relais ne confirme pas la fin.
- **Pré-autorisation** : l’actuel `input_characters` couvre les messages clients seulement (app.py:631, 643–646). L’ajout du prompt système augmente tokens facturables et doit être inclus au maximum prélevable pour éviter une charge au-delà du solde autorisé.
- **Identifiant de discussion** : aucun créateur de discussion ni ID n’est visible dans static/app.js; la stabilité par tour, reprise après reload, expiration, unicité et création de `ChatContext` sont à décider. `build_context` retourne 404 en absence de contexte (services/context_payload.py:49–55); le tool ne pourra pas réussir si le navigateur transmet un ID sans enregistrement/context associé.
- **Instruction système et tool** : le texte exact injecté, le nom attendu par le tool (`discussion_id`, `id_discussion` ou autre), la façon dont le modèle transmet l’argument, et le fait que le tool accepte les IDs UUID sont à confirmer avec son code/configuration Open WebUI, non présent dans `/coach`.
- **Dépendances** : `socketio` n’est utilisé que par `chat()` dans `app.py:666–900`, mais `requirements.txt:12–13` déclare `python-socketio` et `websockets`; avant de les retirer, vérifier les autres unités/scripts et l’usage de l’environnement partagé. Le plan de refonte n’exige pas le redémarrage du service ni l’application immédiate de changements.
